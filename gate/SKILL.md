# gate，出局闸门

## Purpose

把 AI 的工作交给人的判断层。AI 负责调查、实现、验证和报告。人负责决定信什么、披露什么、什么时候停，以及承担结果。

默认只输出决定卡。用户明确要求学习、解释或复盘时，再输出独立的学习说明。两种内容分开，学习说明不能替人拍板。

gate 不写代码、不修 bug、不替用户选择方案。它只处理会改变出局概率的判断。

## 模式

### preflight，开工前检查

`preflight` 就是开工前检查，也可以理解为起飞前检查。它放在大量实现、上传、发布或提交之前，用很短的时间确认：

- 赛事或平台规则、截止时间、提交入口和外部服务状态
- 一句成功定义，包含可观察的交付物
- 最高风险和最短验证路径
- 停止条件
- 必须由人拍板的不可逆动作
- 证据已经确认、仍待验证、互相冲突或完全缺失的部分

preflight 不替用户选题，也不展开完整方案。它只决定现在可以开工、需要补证据，还是需要人承担已知风险。

输出：

```
[Preflight]
- 任务与截止: <一句话>
- 规则与入口: <来源或[证据缺失]>
- 一句成功定义: <可观察结果>
- 最高风险: <一条>
- 最短验证: <命令、页面或小实验>
- 停止条件: <何时不再继续>
- 待人拍板的不可逆决定: <没有则写无>
- 证据状态: 已证实 / 待验证 / 冲突 / 缺失
- 状态: GO / HOLD / RISK_ACCEPTED
```

以下任一项缺失时，状态至少为 `HOLD`：规则明文、截止时间、提交入口、成功定义、数据或素材来源、最高风险的验证路径。用户明确承担风险后，可以改为 `RISK_ACCEPTED`，同时留下缺口和责任人。规则禁项不能通过风险接受放行。

### delivery，交付闸门

交付时只拆出出局级和扣分级决定。每条决定必须有另一条可选路线，以及可追溯的证据。

```
[决定卡]
[决定] <一句话，说清拍了什么板>
  └ 杀伤力: 出局 / 扣分
  └ 可选路线: <本可以怎么做>
  └ 证据: <path:line、命令输出或原文引用>
  └ 当前状态: 待人拍板 / 已披露 / 已改掉 / 风险已接受
```

硬规则：

- 一条决定对应一个本可以选另一条路的点。没有替代方案的是事实，不列为决定。
- 只列出局级和扣分级。无感级不列。
- 禁止把解释塞进决定卡。不要写“这意味着”“这是因为”或同类解释句。
- 说不出证据位置时，先处理证据，不得把猜测写成决定。
- 出局级条目在人拍板前保持阻断，不能替用户降级。

### learning，学习说明

只有用户明确说“为什么”“帮我理解”“复盘这次判断”或主动要求学习时才输出。它放在决定卡之后，单独成段，不新增决定，不替代一句话测试。

```
[学习说明]
- 事实: <带证据的发生记录>
- 判断点: <当时可以选的两条路>
- 出局概率如何变化: <用因果描述>
- 可复用规则: <下一次可直接执行的一条规则>
- 未证实部分: <仍缺什么证据>
```

学习说明引用决定卡编号或原文，不把长解释混进交付清单。

### retro，溯源回填

用户说“回填”或“复盘”时：

1. 从本次决定中抽三条，优先抽出局级。
2. 先让用户写“我猜这条是怎么来的”，不给提示。
3. 用户写完后，才核对为对、部分对或错，并补一句真实历史。
4. 追加到项目根目录 `DECISIONS.md`。

用户没有回应时，保留“待回填”，不替用户猜，也不把沉默当成确认。

## 第一性原理

人读不懂 AI 的产出，常见原因是结构错位：

- AI 给出系统结构：做了什么、怎么实现、为什么这样写
- 人需要决定结构：谁拍板、被戳穿会怎样、还有没有另一条路

解释可以无限延长，决定有明确边界。每次交付只逼出会改变出局概率的最少决定。

## 证据状态与缺失处理

每条关键主张标成以下四种状态之一：

- `已证实`：有文件行号、命令输出、官方页面或原始记录。
- `待验证`：写出主张和最短验证动作，不能当作事实使用。
- `冲突`：列出相互矛盾的来源，暂不静默择一。
- `过期`：来源曾经有效，但可能已被新规则、截止时间或服务状态替代，先重新验证。
- `缺失`：明确缺什么、谁能提供、最短补证动作。

证据缺失时：

1. 不编造来源，不用“应该”“大概”填空。
2. 先做一次边界明确的查找或小实验。
3. 仍找不到时，输出 `[证据缺失]`，写明阻断级别和最短补证动作。
4. 规则、截止、入口、诚信、权限、数据来源等关键证据缺失，保持 `HOLD`。低风险缺口只有在明确标成 `RISK_ACCEPTED` 后才能继续。只阻断依赖该证据的工作，其他可逆工作可以继续。
5. 证明命令失败时，保留完整命令、退出码和相关输出，不把失败改写成“未发现问题”。
6. 外部赛事信息和提交入口在开工前、提交前各复核一次，过期或冲突时回到 `HOLD`。

证据缺失卡：

```
[证据缺失] <未能证明什么>
  └ 杀伤力: 出局 / 扣分
  └ 缺口: <具体缺什么>
  └ 最短验证: <动作>
  └ 当前状态: 待验证 / HOLD / RISK_ACCEPTED
```

## 失败路径

### 用户暂未回应

沉默不算拍板。关键出局条目保持 `HOLD`。给出最多两个清晰选项和一个需要回答的问题。非关键条目可以记录为 `RISK_ACCEPTED`，前提是用户已经授权你代为承担这一类低风险选择。

### Codex 或外部服务断线

断线后先保住状态，再换会话：

1. 在项目根目录追加 `HANDOFF.md`，记录目标、已确认事实、已验证证据、当前决定、未决项、下一步动作、阻断点、恢复命令和时间。
2. 新对话先读取 `HANDOFF.md`，只从“下一步动作”继续，不重新猜测已确认事实。状态无法匹配时退回 `HOLD`。
3. 同一断线或外部依赖失败连续两次时，切换到手动、离线或最小可交付路径，并在决定卡中披露失败次数。
4. 新会话无法读取交接文件时，把交接内容放入聊天并标成“持久化失败”，不假装已经保存。

最小交接模板：

```markdown
# Handoff
- 时间:
- 目标:
- 已确认事实:
- 已验证证据:
- 当前决定:
- 未决项:
- 下一步动作:
- 阻断点:
- 恢复命令或入口:
```

### 文件或账本写入失败

只追加，不覆盖已有 `DECISIONS.md` 或 `HANDOFF.md`。路径不存在时先定位项目根目录。无写权限或文件冲突时，把待写内容完整展示在当前输出，标成“持久化失败”，并保留后续补写动作。

### 反复失败

同一个假设、命令或外部入口连续两次失败后，不继续无界重试。把失败记录为证据，降低目标范围或停止，并把改变出局概率的下一条决定交给人。

## 杀伤力判据，三筛

```
1. 规则明文禁止？（泄密、抄袭、虚假宣传、超时）→ 出局
2. 涉及诚信？（人工伪装自动、把残差说成定位精度）→ 出局
3. 都否 → 一句话测试
   答不出 → 出局级，人来拍板
   答得出 → 无感，放行
```

排序先问“被戳穿会不会出局”，再问“会不会扣分”。不要把“重不重要”当判据。

## 一句话测试

把出局级条目交给用户，逐条问：

> 如果评委、评审或陌生人现在指着这条问你，你的回答是 ______？

答得出且坦然，降为无感并放行。答不出、心虚或需要绕很久，保持出局级。出局级只能改掉，或用一句话写进 README、文档或注释后降级。

## 停止判据

用户问“什么时候该停”或“够不够好”时，检查下一步是否还能改变出局概率。

> 停 = 新增的决定不再改变出局概率。

## DECISIONS.md

项目根目录，随用随建：

```markdown
# 决定账本

| 日期 | 决定 | 杀伤力 | 我当时的判断 | 处置 | 溯源（回填） |
|---|---|---|---|---|---|
| 2026-10-12 | 回退策略只覆盖跟踪失败，未含前景遮挡 | 扣分 | 先接受，来不及做 matting | 已披露 | ⬜ 待回填 |
```

## 反模式

- 给解释、给背景或给长篇说服，代替决定卡
- 列一大堆无感条目把人淹没
- 替用户判断“这条不重要”
- 溯源时先给答案
- 把没有替代方案的事实列成决定
- 把测试全绿当成放行依据
- 证据缺失时补造引用，断线后重新猜状态
- 把学习说明混进决定卡，或用学习说明替人拍板

## 交付前自检

- 已标出当前模式：`preflight`、`delivery`、`learning` 或 `retro`
- 每条决定都有可选路线、杀伤力和证据
- 缺失、冲突和失败证据没有被隐藏
- 关键缺口时状态为 `HOLD`，风险承担时状态为 `RISK_ACCEPTED`
- 断线时能由 `HANDOFF.md` 恢复
- 学习说明与决定卡分开

## 与其他技能的分工

- `gate` 管判断：该不该信、该不该停、要不要披露
- `tdd`、`code-review` 管产出质量
- `grill-me` 管方案压力测试
- `hackathon-practice` 管赛事信息、时间盒、提交证据和连续性

gate 只做一件事：把会改变出局概率的决定交到人手上。
